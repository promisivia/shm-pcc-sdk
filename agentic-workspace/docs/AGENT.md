# Website 文档持续迭代规则

本规则用于持续维护 `/home/wfn/pccshm-sdk/website` 下的文档站点。目标不是一次性补文档，而是建立一个可反复执行的文档迭代流程，让新增功能、代码重构、接口变化都能稳定反映到网站中。

## 1. 范围与目标

- 维护对象：`website/`
- 主要文档源：`website/zh/docs/`
- 参考约束：`website/AGENT.md`
- 当前主结构：
  - `website/zh/docs/content/`
  - `website/zh/docs/components/`
  - `website/zh/docs/guides/`
  - `website/zh/docs/api/`

文档迭代必须服务于以下目标：

- 让读者知道这个 SDK 有什么、适合什么场景。
- 让读者知道某个模块怎么用、依赖什么、限制什么。
- 让开发者知道新功能怎么接入、怎么扩展、怎么排查问题。
- 让接口文档能稳定追上代码，而不是长期滞后。

## 2. 固定角色

每次文档迭代至少有两个角色，不能混成一个“写完就算”的动作。

### Writer

负责产出或修改文档，职责包括：

- 明确本次迭代涉及的模块、代码路径、用户场景。
- 先读代码与已有文档，再动笔。
- 按模块规则写文档，而不是自由发挥。
- 对涉及命令、路径、接口名、结构体名的内容做实际核对。
- 更新导航、索引、交叉链接，避免孤立页面。

### Checker

`Checker` 是每次迭代的指定检查者，默认必须存在，且职责独立于 Writer 的写作动作。

`Checker` 的职责包括：

- 检查文档内容是否和当前仓库代码一致。
- 检查页面是否放在正确模块下，而不是随意堆放。
- 检查是否存在“描述了意图，但没有给出可执行信息”的空话。
- 检查命令、路径、头文件、函数名、目录名是否可在仓库中定位。
- 检查是否遗漏前置条件、限制条件、失败场景、兼容性说明。
- 检查 `toctree`、入口页、上下游页面之间的链接是否完整。
- 检查自动生成页面是否误改手写区/自动区边界。

如果本轮只有一个执行者，也必须先完成 Writer 工作，再按 Checker 清单重新审核一次，输出明确的检查结论。

## 3. 每次迭代的标准流程

每次更新 `website` 文档时，按以下顺序执行：

1. 定义变更范围
2. 定位对应模块
3. 阅读代码与现有文档
4. 判断是“修订现有页”还是“新增页面”
5. 按模块规则写作
6. 更新索引、导航、交叉链接
7. 由 `Checker` 按检查清单验收
8. 记录本轮结论与后续待补项

禁止跳过第 2、3、6、7 步。

## 4. 单次迭代的输出格式

每次迭代完成后，至少要能回答以下问题：

- 本次更新了哪个模块
- 对应代码来源是什么
- 面向哪类读者
- 新增/修改了哪些页面
- 哪些信息已确认来自代码
- 哪些内容仍是待确认项

建议每次迭代在提交说明、任务说明或工作日志中采用以下模板：

```md
## 文档迭代记录

- 范围：
- 读者：
- 代码依据：
- 更新页面：
- 主要新增信息：
- Checker 结论：
- 待补项：
```

## 5. 通用写作规则

所有模块都必须遵守以下规则：

- 先写“读者能做什么”，再写背景解释。
- 优先引用真实代码、真实目录、真实接口，避免抽象空话。
- 命令、路径、函数名、类型名必须可在仓库中定位。
- 一页只解决一个主要问题，不要把多个主题混写。
- 页面开头必须说明适用对象和使用场景。
- 页面中必须出现限制条件、前置条件或依赖项，不能只写 happy path。
- 有顺序的操作必须用步骤写清楚。
- 有代码依据的内容优先使用 `literalinclude` 或明确指向真实文件。
- 不写“这里将介绍”“本节旨在说明”这类元话术，直接给信息。
- 不复制大段代码到文档中，除非片段很短且必须内联解释。
- 新页面必须补到对应 `index.md` 的 `toctree` 中。
- 修改页面时要顺手检查相关入口页是否需要更新摘要。

## 6. Checker 验收清单

`Checker` 必须逐项检查，不能只做泛泛阅读。

- 结构检查：页面位置是否属于正确模块。
- 导航检查：是否更新了对应 `index.md` 或入口链接。
- 事实检查：函数、路径、命令、目录、模块名是否真实存在。
- 场景检查：页面是否清楚说明适用场景与不适用场景。
- 步骤检查：操作步骤是否完整，是否缺前置条件。
- 示例检查：示例是否来自仓库真实代码，或明确标注为伪代码。
- 一致性检查：术语是否和现有文档一致。
- 生成规则检查：`func_api.md` 自动生成区是否未被手改。
- 可维护性检查：是否避免与代码强绑定但易过时的重复描述。
- 完整性检查：是否补充了相关页面的交叉引用。

验收输出必须是明确结论之一：

- `PASS`：可合入
- `PASS WITH FOLLOW-UPS`：可合入，但列出待补项
- `BLOCKED`：不能合入，必须返工

## 7. 模块级写作规则

### 7.1 `content/` 规则

适用于总览类、架构类、仓库结构类文档。

应写内容：

- 这个部分回答“这个 SDK 有什么、为什么这么分、从哪里开始看”。
- 说明核心模块关系，而不是罗列所有细节。
- 给读者建立心智模型：组件边界、数据流、职责分层、仓库布局。

页面结构建议：

1. 这页回答什么问题
2. 核心概念/总体结构
3. 关键模块关系
4. 代码入口或目录入口
5. 延伸阅读

禁止事项：

- 不把 `content/` 写成 API 手册。
- 不在这里展开过长的操作步骤。
- 不堆砌口号式介绍，必须落到真实目录与真实模块。

### 7.2 `components/` 规则

适用于组件使用说明，如数据结构、RPC、apps。

应写内容：

- 组件解决什么问题
- 组件依赖什么运行前提
- 使用入口在哪里
- 最小可运行路径是什么
- 常见配置、关键结构、典型调用链是什么
- 有哪些限制、边界、坑点

页面结构建议：

1. 组件用途
2. 前置条件
3. 关键文件与代码入口
4. 最小使用流程
5. 关键数据结构/接口
6. 常见问题或限制
7. 相关页面

禁止事项：

- 不只写“组件概念”，必须写“怎么落地使用”。
- 不给出无法在仓库复现的命令和路径。
- 不省略失败条件和限制条件。

### 7.3 `guides/` 规则

适用于开发指南、扩展指南、调试说明、多进程/消息队列等专题。

应写内容：

- 一条完整任务链路，例如“如何新增能力”“如何接入功能”“如何完成一次开发动作”。
- 明确读者是谁，默认假设其已经具备什么背景。
- 给出步骤、检查点、常见错误和回滚/修正方式。

页面结构建议：

1. 目标与适用读者
2. 前置知识/环境
3. 分步骤操作
4. 每一步的验证方式
5. 常见错误
6. 延伸链接

禁止事项：

- 不把 guide 写成散文式介绍。
- 不跳过验证步骤。
- 不只讲原理，不讲具体操作。

### 7.4 `api/` 规则

适用于接口索引、头文件说明、函数/类型说明。

应写内容：

- 先说明模块边界和使用时机，再进入接口列表。
- 说明接口分组原则，例如按头文件、子模块、职责划分。
- 对关键接口补充调用约束、线程/生命周期/内存语义。

页面结构建议：

1. 模块简介
2. 头文件或子模块划分
3. 关键类型/函数说明
4. 使用约束
5. 相关示例或上层页面链接

特殊规则：

- `website/zh/docs/api/func_api.md` 的自动生成区禁止手改。
- 手写说明只放在自动生成标记之前。
- 对自动生成 API 的补充说明，应写“如何理解/何时使用/有哪些限制”，不要重复生成内容。

## 8. 入口页与索引页规则

以下页面不是普通内容页，更新时必须额外检查：

- `website/zh/docs/index.md`
- `website/zh/docs/content/index.md`
- `website/zh/docs/components/index.md`
- `website/zh/docs/guides/index.md`
- `website/zh/docs/api/index.md`

规则：

- 每个索引页都要回答“这一组页面解决什么问题”。
- 每新增一个页面，都要判断是否需要挂到相应索引页。
- 索引页的描述要简短，但必须能区分子页面职责。
- 不允许出现页面已经存在，但入口页没有链接的情况。

## 9. 多语言规则

仓库存在 `zh/`、`docs/`、`en/` 等多套内容。默认以当前实际维护主线为准，但每次迭代都必须判断是否存在语言同步义务。

最低要求：

- 如果本次只更新中文主文档，要在记录中说明英文是否暂不同步。
- 不允许出现中文已重构页面结构，但英文入口仍指向旧结构却无人标注。
- 若暂不做翻译，至少在工作记录中标明“中文优先，英文待补”。

## 10. 触发迭代的事件

以下事件发生时，应主动触发一次文档检查，而不是等到最后统一补：

- 新增目录、模块、组件
- 公开接口变化
- 初始化/构建/运行方式变化
- 示例代码路径变化
- 多进程、多机、消息队列、共享内存语义变化
- 导航结构调整

## 11. 禁止事项

- 禁止脱离代码凭印象写接口说明。
- 禁止把任务说明、提示词、写作意图直接写进正式文档。
- 禁止新增页面后不更新 `toctree`。
- 禁止手工修改自动生成区。
- 禁止用泛化描述替代真实路径、真实模块、真实命令。
- 禁止只补“功能介绍”而不补“如何验证”和“限制条件”。

## 12. 默认执行策略

如果没有额外说明，后续所有 `website` 文档任务默认采用以下策略：

- 先判断任务属于 `content/components/guides/api` 哪一类。
- 由 Writer 按对应模块模板写作。
- 由 `Checker` 按第 6 节清单验收。
- 未通过验收的页面不视为完成。

本文件是 `website` 文档持续迭代的工作规则入口。后续若需要细化某一模块，可以在 `agentic-workspace/` 下继续拆分更细的专题规则文件，但不得与本规则冲突。
